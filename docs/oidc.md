# OIDC

All Authelia clients are configured in `apps/authelia/helm/configuration.yaml.tmpl` following the official Authelia client integration guides: pre-configured one-week consent is universal. PKCE (S256) and RS256 token signatures apply to every client; the only unsigned-access-token client is the Envoy Gateway client (`envoy`, which authenticates the gateway-OIDC routes below — Envoy's oauth2 filter does not send PKCE, and its access token stays opaque because it never leaves Envoy's encrypted session cookie and no claims are read from it). `velero-ui` keeps RS256-signed tokens but is the one client where PKCE cannot be required (its passport-oauth2 flow sends no PKCE). Three clients deviate from the confidential-client `client_secret_basic` token-endpoint auth method and use `client_secret_post` instead, each inline-justified in the template: Home Assistant's `hass-oidc-auth` plugin, the RustFS console, and velero-ui cannot send Basic auth headers.

A shared `apps` claims policy embeds `preferred_username`, `email`, `name`, and `groups` in ID and access tokens. Recent Authelia releases stopped placing these claims in ID tokens by default (they are served via the UserInfo endpoint), and clients that read claims from the token — Argo CD notably runs without `enableUserInfoGroups` — require the policy to keep group-based role mapping working. Clients needing custom role claims (`immich_role`, OpenCloud's group list) have dedicated policies following the custom-claim pattern.

Browser-UI routes without usable app-native auth are authenticated by Envoy Gateway itself as the shared `envoy` client — an HTTPRoute-scoped SecurityPolicy per host, access gated to the `platform` group (see the envoy-gateway row). The pattern applies only to browser-UI routes: non-browser clients cannot complete the OIDC redirect flow, so CalDAV/CardDAV (OpenCloud's proxy to Radicale, used by DAVx5), Collabora's WOPI route, the OpenChamber and Paseo routes to the agents VM (app clients and Paseo pairing), the RustFS operator console, and the Notesnook stack keep app-native access controls, and headless probes of protected routes (Homepage siteMonitors) are removed rather than exempted.
