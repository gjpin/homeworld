# Network Connections

All applications enforce default-deny egress via Cilium Network Policies, with baseline access granted to internal cluster DNS (`kube-system/kube-dns:53`) — except `csi-driver-nfs` (no rules beyond default-deny: its only pod is the host-network node plugin, outside Cilium policy scope, which mounts the NAS from the node) and `qbittorrent`, whose DNS egress is scoped per selector to match its WireGuard DoT setup. Host-network pods (Cilium's agents, the csi-driver-nfs node plugin, the k3s upgrade Jobs, kube-vip) are outside Cilium policy scope; firewalld guards the nodes themselves ([fedora.md](fedora.md#firewall)), and the agents VM is confined by the Ryzen's firewalld policies ([openchamber.md](openchamber.md#network)). Workload connections below detail all permitted ingress sources, internal cluster destinations, and outbound internet access.

## Kubelet probes under default-deny

Cilium's Kubernetes-mode policy engine carries an implicit ALLOW for traffic from the local host (the reserved `host` identity) to local pods, below explicit deny rules but above the default-deny fallback — exactly so kubelet readiness/liveness probes survive default-deny ingress policies. This cluster runs the veth datapath with kube-proxy replacement and the host firewall disabled, which preserves that behavior. The `fromEntities: host` probe rules that exist on a few components (qbittorrent, radicale) are therefore redundant defense-in-depth, not a requirement. Revisit if the datapath mode changes (netkit had probe regressions upstream), the host firewall is enabled, or `allow-localhost` is switched away from its Kubernetes-mode default.
