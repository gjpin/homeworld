## Sync waves
* **Sync wave -1**
   * admission-policies: CEL ValidatingAdmissionPolicies protecting Pod Security Admission labels
   * prometheus-operator-crd: CRDs required by service monitors, ahead of Argo CD's own ServiceMonitors
   * external-secrets: External Secrets Operator, Infisical ClusterSecretStore, and the ExternalSecret CRD, ahead of Argo CD's own wave -1 ExternalSecret
* **Sync wave 0**
   * argocd: the homeworld Config Management Plugin that renders every
     application ([below](#homeworld-plugin));
     Argo CD is first installed by `host/bootstrap.sh` through the k3s
     auto-deploying manifests directory with `bootstrap/argocd-values.yaml`
     ([docs/k3s.md](k3s.md#first-server)), and this application adopts that
     release on its first sync; its nested `argocd-valkey` application
     (intra-component wave 0) provides the Valkey instance the tracked
     config points Argo CD at (`externalRedis`)
* **Sync wave 1**
   * none — wave 1 is the intra-component workload wave; no root applications are sequenced here
* **Sync wave 2**
   * envoy-gateway: Gateway API implementation and the Envoy Gateway CRDs
     required by its policies (the Gateway API CRDs themselves come from k3s)
   * cilium: kube-proxy-free CNI lifecycle; the CNI itself is bootstrapped
     by `host/bootstrap.sh` ([docs/k3s.md](k3s.md)) and the Argo CD
     application adopts it, sequenced after prometheus-operator-crd so the
     chart's ServiceMonitors validate

     Let's Encrypt ClusterIssuers (DNS-01 through Cloudflare)
   * external-dns: publishes the wildcard record pointing every name under
     the domain at the Gateway VIP; its `DNSEndpoint` CRD ships with the
     chart (wave-1 Helm Application) and the `DNSEndpoint` itself syncs at
     intra-component wave 2 with `SkipDryRunOnMissingResource=true`
   * longhorn: block storage
   * snapshot-controller: CSI volume snapshot CRDs (from the pinned
     `external-snapshotter` Git tag) and the handwritten snapshot
     controller driving the Longhorn CSI driver; Velero's CSI snapshot
     data movement consumes this suite
   * kubelet-serving-cert-approver: approves the kubelet serving certificate
     signing requests generated by the rotating kubelet certificates the k3s
     configuration enables ([docs/k3s.md](k3s.md#k3s-configuration))

     approved serving certificates; it shares wave 3 with the
     kubelet-serving-cert-approver, so their relative order within the wave
     comes from Argo's kind-based sorting rather than a wave guarantee (the
     approver re-approves any rejected scrape, so a race self-heals)
     over the approved serving certificates, after prometheus-operator-crd
     (ServiceMonitors) and the kubelet-serving-cert-approver

   * grafana-operator: Grafana instance, dashboard, and datasource operator
   * mariadb-operator: MariaDB operator, its validating webhook, and the

* **Sync wave 5**

   * victoria-metrics: VictoriaMetrics (metrics), VictoriaLogs (logs), and VictoriaTraces (traces) backend,

   * velero-ui: web interface for Velero, after the Velero server

## Homeworld plugin

The cluster domain is not in git. Wherever it belongs, manifests carry the
placeholder `base-domain.invalid` (`.invalid` is reserved and never
resolves, so a missed substitution fails visibly), and every Application
sourced from this repository names the `homeworld` Config Management Plugin
(`spec.source.plugin.name: homeworld`) instead of relying on Argo CD's
built-in source detection.

The plugin (`configs.cmp` in `apps/argocd/helm/values.yaml`) runs as the
`homeworld-plugin` sidecar of the repo-server, on the Argo CD image itself.
For a directory holding a `kustomization.yaml` it runs
`kustomize build --enable-helm` with the same `--helm-kube-version` and
`--helm-api-versions` arguments the built-in Kustomize tool would pass;
otherwise it concatenates the directory's YAML files, as a plain directory
source would. It then replaces `base-domain.invalid` with the domain from
the `homeworld-domain` Secret in `argocd`, and refuses to render when that
value is missing or is not a domain, so the placeholder never reaches the
cluster.

The Secret comes from Infisical (`/argocd/BASE_DOMAIN`, [secrets.md](secrets.md)).
Rendering anything, External Secrets included, needs it, so
`host/bootstrap.sh` reads the key once with the External Secrets machine
identity and seeds the Secret before Argo CD starts
([k3s.md](k3s.md#first-server)); the `homeworld-domain` ExternalSecret
(`apps/argocd/-1_secrets.yaml`) adopts it afterwards and keeps it in sync.
The sidecar mounts the whole Secret, so a changed domain reaches it without
a restart; Argo CD re-renders on its next manifest refresh (hard-refresh to
force it). The bootstrap install merges the plugin's values from
`apps/argocd/helm/values.yaml` into `bootstrap/argocd-values.yaml`, so both
installs run the same plugin.

## Application Health Checks

Argo CD does not evaluate the health of `argoproj.io/Application` CRDs by default; custom resources without a defined health check are treated as immediately `Healthy` upon creation. In an App-of-Apps pattern, this default causes the parent application to advance through sync waves immediately without waiting for child applications or their underlying workloads to reconcile.

This cluster used to set a custom Lua health check (`resource.customizations.health.argoproj.io_Application`) in `argocd-cm` for that purpose; it was removed because it duplicated Argo CD's built-in Application health assessment while dropping the built-in `operationState` mapping (so a sync in progress never showed `Progressing`). The built-in assessment provides the same wave gating Argo CD is documented to have out of the box for Application resources: a child application's `status.health` (and any running operation's `operationState`) roll up to the parent's App-of-Apps view.

### Behavior
- **Default State:** Argo CD's built-in assessment marks a newly declared or reconciling child application `Progressing` and reports `Healthy` only once the child and its managed resources reconcile (running operations surface through `operationState`).
- **Status Rollup:** Once the child application and all its managed resources reconcile, its health status (`Healthy`, `Progressing`, `Degraded`) is bubbled up to the parent application.
- **Wave Gating:** Sync waves in `apps/app-of-apps.yaml` pause at wave $N$ until every application in that wave reaches `Healthy` before proceeding to wave $N+1$.

### Custom resource health checks

`argocd-cm` (`apps/argocd/helm/values.yaml`) adds one health check for a kind
Argo CD does not cover: `k8s.mariadb.com/PhysicalBackup`. Supernote's
pre-upgrade backup is a PreSync hook, and Argo CD only waits for a hook whose
health it can assess — without the check the snapshot would be marked
`Healthy` on creation and the MariaDB image would roll before it exists. A
one-shot backup is `Progressing` until its `Complete` condition is `True`
and `Degraded` when the snapshot fails (failing the sync); "MariaDB not
found"/"not ready" report `Healthy` so the first sync and repair syncs are
not wedged; scheduled backups stay `Healthy` between runs.

Argo CD's bundled health checks also make three kinds wave barriers here,
each held `Progressing` until its controller reports status:

- CNPG `Database`: `Healthy` once the operator has applied the current
  generation, so an extension the image lacks holds the component's later
  waves.
- Envoy Gateway `SecurityPolicy`: `Healthy` once accepted on the Gateway and
  `Degraded` when rejected, such as with a missing client secret. Every gateway
  OIDC policy therefore sets `authorizationEndpoint` and `tokenEndpoint`
  explicitly. Without them Envoy Gateway fetches the issuer's discovery
  document, and Authelia installs in a later root wave than the policies of
  `envoy-gateway`, `longhorn`, and `victoria-metrics`, so the policy would be
  rejected and the root waves would stall ahead of it.
- Velero `Schedule`: `Healthy` once enabled, `Degraded` on failed validation.

## Universal Server-Side Apply

Every Argo CD `Application` resource in this repository—both root applications in `apps/app-of-apps.yaml` and child applications in `apps/<component>/`—enables Server-Side Apply by default:

```yaml
syncPolicy:
  syncOptions:
    - ServerSideApply=true
```

### Rationale & CRD Upgrades
- **256 KB Annotation Limit:** Standard client-side apply serializes the full resource configuration into the `kubectl.kubernetes.io/last-applied-configuration` annotation. Modern Custom Resource Definitions (CRDs)—such as Prometheus Operator, Gateway API, Cert-Manager, and CloudNativePG—regularly exceed the 256 KB annotation size ceiling, causing client-side apply sync operations to fail.
- **CRD and Schema Evolution:** Server-Side Apply offloads merge calculation and field ownership to the Kubernetes API server (`fieldManager: argocd`). This enables declarative CRD upgrades and schema changes without requiring manual kubectl intervention.
- **Server-Side Diff:** `ServerSideApply=true` also selects Server-Side Diff for the Application: the controller dry-runs a Server-Side Apply against the API server for every resource that already exists (a resource not yet created gets a plain diff with no API call, so a missing CRD does not fail it). A dry-run the API server or a validating webhook rejects, such as a change to an immutable field, raises a `ComparisonError` on the whole Application instead of only failing at sync.
- **Universal Uniformity:** Enforcing SSA globally prevents future CRD additions from failing silently or encountering annotation overflow.

## CRD Lifecycle and Upgrade Management

CRD lifecycles are orchestrated through a combination of sync waves, health checks, and Server-Side Apply to guarantee that Custom Resource Definitions are established and upgraded before the workloads that depend on them:

### Consumer Workload Sequencing (App-of-Apps Waves)
In `apps/app-of-apps.yaml`, CRD-providing infrastructure and operators are sequenced strictly ahead of consuming applications:
- **Wave -1:** `prometheus-operator-crd` (ServiceMonitor/PodMonitor/ScrapeConfig CRDs) and `external-secrets` (ExternalSecret CRD and the Infisical `ClusterSecretStore`), both ahead of `argocd` in wave 0 so Argo CD's own ServiceMonitors and its wave -1 ExternalSecret validate on the first install; the monitoring CRDs are later consumed cluster-wide by the OpenTelemetry Operator's Target Allocator (wave 5)
- **Wave 0:** `argocd` — Argo CD's tracked config replaces the chart's bundled Redis with an in-namespace Valkey instance through the chart's `externalRedis` block; the nested `argocd-valkey` application syncs it at intra-component wave 0, ahead of the wave-1 Argo CD release, and needs no operator
- **Wave 2:** `envoy-gateway` (Envoy Gateway CRDs; the Gateway API CRDs are installed by k3s before Argo CD exists) and `cilium` (Cilium CRDs applied from the pinned Git tag by the nested `cilium-crds` application; the Helm chart ships no CRDs, while the CiliumNetworkPolicy CRDs are consumed by every component's `-2_network_policy.yaml`)
- **Wave 3:** `cert-manager` (Certificates and ClusterIssuers), `external-dns` (the `DNSEndpoint` CRD from its chart, ahead of its intra-component wave-2 `DNSEndpoint`), `snapshot-controller` (CSI volume snapshot CRDs from the pinned `external-snapshotter` Git tag plus the handwritten snapshot controller — the CSI snapshot API suite Velero's data movement drives, installed ahead of the wave 4 backup operator), `system-upgrade-controller` (the `Plan` CRD from the pinned release tag, ahead of its Plans), plus the `longhorn`, `csi-driver-nfs`, `kubelet-serving-cert-approver`, and `metrics-server` applications
- **Wave 4:** `velero` (backup operator, after the snapshot-controller suite) and the datastore operators (`cloudnative-pg`, `mariadb-operator`, `rustfs-operator`, `grafana-operator`)
- **Wave 5:** `velero-ui` (web interface for Velero), `rustfs` (shared S3-compatible Tenant), `victoria-metrics` (the metrics/logs/traces backends and vmalert), the `documentdb-operator` (DocumentDB CRDs plus the CNPG-I sidecar
  injector plugin, which must live in the `cloudnative-pg` namespace for
  CloudNativePG plugin discovery), and the `opentelemetry-operator`
  (OpenTelemetryCollector/TargetAllocator CRDs, rendered through the chart's
  `conf/crds` templates so Kustomize Helm inflation includes them), whose
  collector custom resource in wave 6 both validates against the CRDs and
  reconciles against the running operator
- **Waves 6–8:** Applications and workloads consuming those CRDs (`authelia`, `immich`, `forgejo`, `grafana`, `affine` via `Cluster` and `ServiceMonitor`, `notesnook` via `DocumentDB`, `supernote` via `MariaDB` and `SqlJob`, `otel-collector` via `OpenTelemetryCollector`, `kube-control-plane` via `ServiceMonitor` and `ScrapeConfig`, `opencloud`, etc.)

Argo CD's custom Lua Application health check pauses wave advancement until all applications in Wave $N$ report `Healthy`, preventing downstream workloads from encountering missing CRD errors during initial deployment or cluster-wide upgrades.

### Declarative CRD Upgrades via Server-Side Apply
Standard Helm (`helm upgrade`) intentionally ignores the `crds/` directory, preventing declarative CRD upgrades. In this repository:
- Operator charts are rendered via Kustomize with `includeCRDs: true`; local rendering therefore requires Helm inflation (`kubectl kustomize --enable-helm` or `kustomize build --enable-helm` — the same flag the homeworld plugin passes, [below](#homeworld-plugin)).
- Every `Application` enforces `ServerSideApply=true`.
- On chart version bumps, Argo CD detects CRD schema changes and applies them directly to the Kubernetes API server using Server-Side Apply (`fieldManager: argocd`), avoiding the 256 KB `kubectl.kubernetes.io/last-applied-configuration` annotation limit.

### Resource Ordering Within Sync Waves
Within an individual sync wave, Argo CD sorts manifests by Kubernetes `Kind` priority, applying `CustomResourceDefinition` resources before controller workloads (`Deployment`, `StatefulSet`, `DaemonSet`).

### Dedicated CRD Applications vs. Bundled Helm Releases
- **Standalone CRDs:** Shared ecosystem CRD suites without local controller dependencies are separated into dedicated Argo CD applications and sync waves: `prometheus-operator-crd` is a root application, while `cilium-crds`, `snapshot-controller-crds`, and `system-upgrade-controller-crds` are child Applications inside their component directories (all four precede every CR consumer). The Gateway API CRDs (standard channel) come from k3s's bundled `gateway-api-crd` addon, which k3s re-applies on every server start and upgrades with every k3s release; the Envoy Gateway chart's own Gateway API CRD copy is patch-deleted from the render (`apps/envoy-gateway/helm/kustomization.yaml`) so k3s stays the single owner. The `cilium` Helm chart ships no CRDs, so `cilium-crds` applies the full `pkg/k8s/apis/cilium.io/client/crds/v2` set from the chart-aligned Git tag; `host/bootstrap.sh` (see [docs/k3s.md](k3s.md)) installs them before Argo CD exists, and the application takes over ownership for declarative upgrades. The v2alpha1 `CiliumL2AnnouncementPolicy` CRD is registered by `cilium-operator` itself on startup, so the `cilium` component applies its L2 announcement policy (`apps/cilium/2_l2_announcement_policy.yaml`) at wave 2, after the wave-1 Helm Application, with `SkipDryRunOnMissingResource=true`. Pruning is deliberately disabled on `cilium-crds`: garbage-collecting the Cilium CRDs would delete every `CiliumNetworkPolicy` in the cluster along with them, cutting all workload networking. Pruning is equally disabled on `snapshot-controller-crds`: garbage-collecting the snapshot CRDs would delete the `VolumeSnapshot` objects referencing every existing CSI snapshot. `prometheus-operator-crd` and `system-upgrade-controller-crds` run the same way (see the header comments in their `0_crds.yaml` manifests): pruning is deliberately disabled there too — garbage-collecting the ServiceMonitor/PodMonitor definitions would delete every live monitor, and garbage-collecting the `Plan` definition would delete the k3s upgrade Plans. When an upstream bundle bump drops a CRD, remove the stale definition by hand.
- **Bundled Operator CRDs:** Operators (`cloudnative-pg`, `cert-manager`, `external-dns`, `external-secrets`, `documentdb-operator`, `opentelemetry-operator`, `longhorn`, `velero`, etc.) bundle their upstream CRDs within their Helm charts, relying on Server-Side Apply and Kind-based sorting for in-place schema upgrades. The `documentdb-operator` chart is vendored and patched under `apps/documentdb-operator/helm/local-charts` (see `scripts/vendor-documentdb-operator.sh`) because its upstream packaging breaks Kustomize's Helm inflation: it bundles a CloudNativePG subchart that collides with the standalone operator and hardcodes the `cnpg-system` namespace. Renovate bumps the vendored `Chart.yaml` version and re-vendors the complete tree in the same PR. The `rustfs-operator` image tag follows the chart's `appVersion`, so the operator binary always matches the `tenants.rustfs.com` CRD shipped in the same chart (the apiserver prunes status fields the CRD does not declare). Helm-hook Jobs are inert under Argo and their immutable specs block chart bumps: Longhorn's `preUpgradeChecker` is disabled (its online version check is a phone-home) and its uninstall Job is patch-deleted, while the post-upgrade cleanup is re-annotated as an Argo CD PostSync hook (`argocd.argoproj.io/hook: PostSync` + `hook-delete-policy: HookSucceeded`) so it runs after every sync with the fresh image and self-deletes instead of breaking upgrades.

## Intra-Component Sync Wave Architecture

While `apps/app-of-apps.yaml` coordinates dependencies across broad system waves (0 through 8), individual component directories use a standardized 5-tier intra-component wave model to sequence dependencies within that component's namespace:

| Tier | Wave | Resource Types | Purpose |
| :--- | :--- | :--- | :--- |
| **Network Isolation** | `-2` (or `-3`) | `CiliumNetworkPolicy` | Enforce egress/ingress firewalling before secrets or pods materialize. |
| **Secret Material** | `-1` | `ExternalSecret` | Fetch and reconcile credentials from Infisical before datastores start. |
| **Datastores & Base** | `0` | CNPG `Cluster`, Valkey (nested Application), RustFS `Tenant`, `PVC` | Provision databases, caches, and storage. |
| **Workloads** | `1` | Child `Application`s, `Deployment`, `StatefulSet` | Deploy application workloads, pods, and backend Services. |
| **Routing & Auth** | `2` | `HTTPRoute`, `GRPCRoute`, `SecurityPolicy` | Attach routes to the shared Gateway (`apps/envoy-gateway`) and their gateway OIDC policies after Services exist. |

`apps/envoy-gateway` is the one component that shifts the routing tiers right by one (monitors `0`, Helm `1`, `Gateway`/`GatewayClass`/`EnvoyProxy` `2`, route and `SecurityPolicy` `3`): its Gateway must be created after the Helm-installed controller and its CRDs, and the route after the Gateway, so the relative order workload → gateway → routes is preserved with distinct waves.

### CRDs and OpenAPI Validation (`SkipDryRunOnMissingResource=true`)
When an application directory deploys both a CRD and custom resources of that kind (e.g. `apps/envoy-gateway`, `apps/cert-manager`, and `apps/external-dns`), Argo CD runs client dry-run validation during initial sync before any wave begins. Because CRDs are not yet registered on the API server during dry-run, `SkipDryRunOnMissingResource=true` is retained to bypass dry-run validation failures on uninstalled CRDs. Intra-component sync waves then apply CRDs at wave 0 and downstream custom resources at subsequent waves.
