# ArgoCD

## Sync waves
* **Sync wave -1**
   * admission-policies: CEL ValidatingAdmissionPolicies protecting Pod Security Admission labels
   * prometheus-operator-crd: CRDs required by service monitors, ahead of Argo CD's own ServiceMonitors
   * external-secrets: External Secrets Operator, Infisical ClusterSecretStore, and the ExternalSecret CRD, ahead of Argo CD's own wave -1 ExternalSecret
* **Sync wave 0**
   * argocd: enables Helm inflation for the Kustomize-rendered chart profiles
   * dragonfly-operator: installs alongside argocd because the argocd
     application's tracked config points Argo CD at its in-namespace
     Dragonfly instance (`externalRedis`) — the operator that reconciles
     that instance must already exist when the controllers switch
* **Sync wave 1**
   * none — wave 1 is the intra-component workload wave; no root applications are sequenced here
* **Sync wave 2**
   * envoy-gateway: Gateway API and provides CRDs required by HTTP/GRPC routes
   * cilium: kube-proxy-free CNI lifecycle; the CNI itself is bootstrapped
     by the manifest apply in [docs/talos.md](talos.md) and the Argo CD
     application adopts it, sequenced after prometheus-operator-crd so the
     chart's ServiceMonitors validate
* **Sync wave 3**
   * cert-manager: TLS certificates management
   * external-dns: manages DNS records
   * longhorn: block storage
   * snapshot-controller: CSI volume snapshot CRDs (from the pinned
     `external-snapshotter` Git tag) and the handwritten snapshot
     controller driving the Longhorn CSI driver; Velero's CSI snapshot
     data movement consumes this suite
   * kubelet-serving-cert-approver: approves the kubelet serving certificate
     signing requests generated by the rotating kubelet certificates Talos
     enables during [bootstrap](talos.md#bootstrap)
   * metrics-server: resource metrics (`kubectl top`, HPA) scraped from kubelets over
     approved serving certificates; it shares wave 3 with the
     kubelet-serving-cert-approver, so their relative order within the wave
     comes from Argo's kind-based sorting rather than a wave guarantee (the
     approver re-approves any rejected scrape, so a race self-heals)
     over the approved serving certificates, after prometheus-operator-crd
     (ServiceMonitors) and the kubelet-serving-cert-approver
* **Sync wave 4**
   * cloudnative-pg: postgresql operator
   * grafana-operator: Grafana instance, dashboard, and datasource operator
   * rustfs-operator: RustFS storage operator, console, and STS endpoint
   * velero: whole-cluster backups after External Secrets and Longhorn
* **Sync wave 5**
   * documentdb-operator: DocumentDB (MongoDB-compatible) operator and its
     CNPG-I sidecar injector plugin, after CloudNativePG
   * crowdsec: PostgreSQL-backed CrowdSec LAPI, Envoy log agent, and AppSec WAF,
     after CloudNativePG and External Secrets
   * victoria-metrics: VictoriaMetrics (metrics), VictoriaLogs (logs), and VictoriaTraces (traces) backend
   * rustfs: shared S3-compatible storage Tenant, after the RustFS Operator,
     External Secrets, and Longhorn
   * velero-ui: web interface for Velero, after the Velero server
   * opentelemetry-operator: OpenTelemetry Collector operator and the
     Target Allocator that consumes the Prometheus Operator
     ServiceMonitor/PodMonitor CRDs, after cert-manager (admission webhook
     certificates) and ahead of the collector custom resource in wave 6
   * generic-device-plugin: TUN device plugin DaemonSet in kube-system;
     Talos's runc 1.2 removed default /dev/net/tun access for unprivileged
     pods, and the plugin restores it to non-privileged workloads that
     request the devic.es/tun resource (the gluetun sidecar in wave 6's
     qbittorrent)
* **Sync wave 6**
   * crowdsec-envoy-bouncer: pinned community Envoy external-auth bouncer,
     after CrowdSec and Envoy Gateway; the Gateway policies remain owned by
     their respective application directories and are fail-closed
   * authelia: OpenCloud identity provider, after CloudNativePG, Dragonfly,
     External Secrets, and Prometheus Operator CRDs
   * homeassistant
   * immich
   * otel-collector: operator-managed collector with its Target Allocator,
     after the OpenTelemetry Operator (CRDs) and VictoriaMetrics (export)
   * kube-state-metrics: cluster-state `kube_*` metrics for the telemetry
     pipeline (the CloudNativePG dashboard's kube_* panels), scraped by the
     same Target Allocator as every other ServiceMonitor
   * forgejo
   * grafana
   * homepage: application dashboard, gateway-OIDC protected (`platform` group)
   * notesnook: fully featured encrypted notes sync server with DocumentDB (MongoDB-compatible on CloudNativePG), SSE, and Monograph
   * radicale: internal CalDAV and CardDAV backend, before OpenCloud's
     authenticated DAV proxy
   * vaultwarden: Bitwarden-compatible password manager (CloudNativePG-backed)
     with optional Authelia SSO
   * qbittorrent: torrent client with a gluetun VPN sidecar and a
     port-forward sync job, after generic-device-plugin (the /dev/net/tun
     device), External Secrets, and the CrowdSec Envoy bouncer
* **Sync wave 7**
   * collabora: standalone Collabora chart and WOPI endpoint
   * woodpecker: CI server and Kubernetes-backend agents, after Forgejo (the
     OAuth source and webhook target)
   * openchamber: persistent AI agent workspace (OpenChamber, OpenCode, Codex
     CLI, Pi agent), after Envoy Gateway, cert-manager, External Secrets,
     Longhorn, and the CrowdSec Envoy bouncer
* **Sync wave 8**
   * opencloud: OpenCloud, Tika, RustFS storage integration, authenticated DAV
     proxy, and routes

## Application Health Checks

Argo CD does not evaluate the health of `argoproj.io/Application` CRDs by default; custom resources without a defined health check are treated as immediately `Healthy` upon creation. In an App-of-Apps pattern, this default causes the parent application to advance through sync waves immediately without waiting for child applications or their underlying workloads to reconcile.

This cluster used to set a custom Lua health check (`resource.customizations.health.argoproj.io_Application`) in `argocd-cm` for that purpose; it was removed because it duplicated Argo CD's built-in Application health assessment while dropping the built-in `operationState` mapping (so a sync in progress never showed `Progressing`). The built-in assessment provides the same wave gating Argo CD is documented to have out of the box for Application resources: a child application's `status.health` (and any running operation's `operationState`) roll up to the parent's App-of-Apps view.

### Behavior
- **Default State:** Argo CD's built-in assessment marks a newly declared or reconciling child application `Progressing` and reports `Healthy` only once the child and its managed resources reconcile (running operations surface through `operationState`).
- **Status Rollup:** Once the child application and all its managed resources reconcile, its health status (`Healthy`, `Progressing`, `Degraded`) is bubbled up to the parent application.
- **Wave Gating:** Sync waves in `apps/app-of-apps.yaml` pause at wave $N$ until every application in that wave reaches `Healthy` before proceeding to wave $N+1$.

## Universal Server-Side Apply

Every Argo CD `Application` resource in this repository—both root applications in `apps/app-of-apps.yaml` and child applications in `apps/<component>/`—enables Server-Side Apply by default:

```yaml
syncPolicy:
  syncOptions:
    - ServerSideApply=true
```

### Rationale & CRD Upgrades
- **256 KB Annotation Limit:** Standard client-side apply serializes the full resource configuration into the `kubectl.kubernetes.io/last-applied-configuration` annotation. Modern Custom Resource Definitions (CRDs)—such as Prometheus Operator, Gateway API, Cert-Manager, and CloudNativePG—regularly exceed the 256 KB annotation size ceiling, causing client-side apply sync operations to fail.
- **CRD and Schema Evolution:** Server-Side Apply offloads merge calculation and field ownership to the Kubernetes API server (`fieldManager: argocd`). This enables declarative CRD upgrades and schema changes without requiring manual kubectl intervention.
- **Universal Uniformity:** Enforcing SSA globally prevents future CRD additions from failing silently or encountering annotation overflow.

## CRD Lifecycle and Upgrade Management

CRD lifecycles are orchestrated through a combination of sync waves, health checks, and Server-Side Apply to guarantee that Custom Resource Definitions are established and upgraded before the workloads that depend on them:

### Consumer Workload Sequencing (App-of-Apps Waves)
In `apps/app-of-apps.yaml`, CRD-providing infrastructure and operators are sequenced strictly ahead of consuming applications:
- **Wave -1:** `prometheus-operator-crd` (ServiceMonitor/PodMonitor CRDs) and `external-secrets` (ExternalSecret CRD and the Infisical `ClusterSecretStore`), both ahead of `argocd` in wave 0 so Argo CD's own ServiceMonitors and its wave -1 ExternalSecret validate on the first install; the monitoring CRDs are later consumed cluster-wide by the OpenTelemetry Operator's Target Allocator (wave 5)
- **Wave 0:** `argocd` and `dragonfly-operator` — Argo CD's tracked config replaces the chart's bundled Redis with an in-namespace Dragonfly instance through the chart's `externalRedis` block, so the operator that reconciles that instance installs in the same wave as the switch; the controllers reconnect while the operand starts (~1 minute, the same transient any Argo CD restart incurs)
- **Wave 2:** `envoy-gateway` (Gateway API and Envoy Gateway CRDs) and `cilium` (Cilium CRDs applied from the pinned Git tag by the nested `cilium-crds` application; the Helm chart ships no CRDs, while the CiliumNetworkPolicy CRDs are consumed by every component's `-2_network_policy.yaml`)
- **Wave 3:** `cert-manager` (Certificates and ClusterIssuers), `snapshot-controller` (CSI volume snapshot CRDs from the pinned `external-snapshotter` Git tag plus the handwritten snapshot controller — the CSI snapshot API suite Velero's data movement drives, installed ahead of the wave 4 backup operator), plus the `external-dns`, `longhorn`, `kubelet-serving-cert-approver`, and `metrics-server` applications
- **Wave 4:** `velero` (backup operator, after the snapshot-controller suite) and the datastore operators (`cloudnative-pg`, `rustfs-operator`, `grafana-operator`)
- **Wave 5:** `velero-ui` (web interface for Velero), `crowdsec` (PostgreSQL-backed LAPI, log agent, and AppSec WAF), `rustfs` (shared S3-compatible Tenant), `victoria-metrics` (the metrics/logs/traces backends), `generic-device-plugin` (TUN device plugin in kube-system), the `documentdb-operator` (DocumentDB CRDs plus the CNPG-I sidecar
  injector plugin, which must live in the `cloudnative-pg` namespace for
  CloudNativePG plugin discovery), and the `opentelemetry-operator`
  (OpenTelemetryCollector/TargetAllocator CRDs, rendered through the chart's
  `conf/crds` templates so Kustomize Helm inflation includes them), whose
  collector custom resource in wave 6 both validates against the CRDs and
  reconciles against the running operator
- **Waves 6–8:** Applications and workloads consuming those CRDs (`authelia`, `immich`, `forgejo`, `grafana`, `notesnook` via `DocumentDB`, `otel-collector` via `OpenTelemetryCollector`, `opencloud`, etc.)

Argo CD's custom Lua Application health check pauses wave advancement until all applications in Wave $N$ report `Healthy`, preventing downstream workloads from encountering missing CRD errors during initial deployment or cluster-wide upgrades.

### Declarative CRD Upgrades via Server-Side Apply
Standard Helm (`helm upgrade`) intentionally ignores the `crds/` directory, preventing declarative CRD upgrades. In this repository:
- Operator charts are rendered via Kustomize with `includeCRDs: true`; local rendering therefore requires Helm inflation (`kubectl kustomize --enable-helm` or `kustomize build --enable-helm` — the same flag Argo CD sets globally via `kustomize.buildOptions` in `argocd-cm`).
- Every `Application` enforces `ServerSideApply=true`.
- On chart version bumps, Argo CD detects CRD schema changes and applies them directly to the Kubernetes API server using Server-Side Apply (`fieldManager: argocd`), avoiding the 256 KB `kubectl.kubernetes.io/last-applied-configuration` annotation limit.

### Resource Ordering Within Sync Waves
Within an individual sync wave, Argo CD sorts manifests by Kubernetes `Kind` priority, applying `CustomResourceDefinition` resources before controller workloads (`Deployment`, `StatefulSet`, `DaemonSet`).

### Dedicated CRD Applications vs. Bundled Helm Releases
- **Standalone CRDs:** Shared ecosystem CRD suites without local controller dependencies are separated into dedicated Argo CD applications and sync waves: `prometheus-operator-crd` is a root application, while `cilium-crds`, `gateway-api-crd`, and `snapshot-controller-crds` are child Applications inside their component directories (all four precede every CR consumer). The Envoy Gateway chart bundles its own Gateway API CRD copy; those bundled CRDs are patch-deleted from the render (`apps/envoy-gateway/helm/kustomization.yaml`) so `gateway-api-crd` stays the single owner — two self-healing ServerSideApply Applications fighting over the same CRDs would flip fields on every sync. The `cilium` Helm chart ships no CRDs, so `cilium-crds` applies the full `pkg/k8s/apis/cilium.io/client/crds/v2` set from the chart-aligned Git tag; Talos bootstrap (see [docs/talos.md](talos.md)) installs them before Argo CD exists, and the application takes over ownership for declarative upgrades. Pruning is deliberately disabled on `cilium-crds`: garbage-collecting the Cilium CRDs would delete every `CiliumNetworkPolicy` in the cluster along with them, cutting all workload networking. Pruning is equally disabled on `snapshot-controller-crds`: garbage-collecting the snapshot CRDs would delete the `VolumeSnapshot` objects referencing every existing CSI snapshot. `gateway-api-crd` and `prometheus-operator-crd` run the same way (see the header comments in their `0_crds.yaml` manifests): pruning is deliberately disabled there too — garbage-collecting the Gateway API definitions would delete every live Gateway/HTTPRoute, and garbage-collecting the ServiceMonitor/PodMonitor definitions would delete every live monitor. When an upstream bundle bump drops a CRD, remove the stale definition by hand.
- **Bundled Operator CRDs:** Operators (`cloudnative-pg`, `cert-manager`, `external-secrets`, `dragonfly-operator`, `documentdb-operator`, `opentelemetry-operator`, `longhorn`, `velero`, etc.) bundle their upstream CRDs within their Helm charts, relying on Server-Side Apply and Kind-based sorting for in-place schema upgrades. Two charts are vendored and patched under `apps/<component>/helm/local-charts` because their upstream packaging breaks Kustomize's Helm inflation: the `documentdb-operator` chart (see `scripts/vendor-documentdb-operator.sh`) bundles a CloudNativePG subchart that collides with the standalone operator and hardcodes the `cnpg-system` namespace, and the `rustfs-operator` chart (see `scripts/vendor-rustfs-operator.sh`) ships the `tenants.rustfs.com` CRD twice under `crds/`, which Kustomize rejects as a duplicate resource ID. Renovate bumps the vendored `Chart.yaml` version and re-vendors the complete tree in the same PR. Helm-hook Jobs are inert under Argo and their immutable specs block chart bumps: Longhorn's `preUpgradeChecker` is disabled (its online version check is a phone-home) and its uninstall Job is patch-deleted, while the post-upgrade cleanup is re-annotated as an Argo CD PostSync hook (`argocd.argoproj.io/hook: PostSync` + `hook-delete-policy: HookSucceeded`) so it runs after every sync with the fresh image and self-deletes instead of breaking upgrades.

## Intra-Component Sync Wave Architecture

While `apps/app-of-apps.yaml` coordinates dependencies across broad system waves (0 through 8), individual component directories use a standardized 5-tier intra-component wave model to sequence dependencies within that component's namespace:

| Tier | Wave | Resource Types | Purpose |
| :--- | :--- | :--- | :--- |
| **Network Isolation** | `-2` (or `-3`) | `CiliumNetworkPolicy` | Enforce egress/ingress firewalling before secrets or pods materialize. |
| **Secret Material** | `-1` | `ExternalSecret` | Fetch and reconcile credentials from Infisical before datastores start. |
| **Datastores & Base** | `0` | CNPG `Cluster`, Dragonfly, RustFS `Tenant`, `Gateway`, `PVC` | Provision databases, caches, listeners, and storage. |
| **Workloads** | `1` | Child `Application`s, `Deployment`, `StatefulSet` | Deploy application workloads, pods, and backend Services. |
| **Routing & Auth** | `2` | `HTTPRoute`, `GRPCRoute`, `SecurityPolicy` | Bind ingress routes and CrowdSec external authentication after Services exist. |

`apps/envoy-gateway` is the one component that shifts the routing tiers right by one (CRDs `0`, Helm `1`, `Gateway`/`GatewayClass`/`EnvoyProxy` `2`, route and `SecurityPolicy` `3`): its Gateway must be created after the Helm-installed controller and the route after the Gateway, so the relative order CRDs → workload → gateway → routes is preserved with distinct waves.

### CRDs and OpenAPI Validation (`SkipDryRunOnMissingResource=true`)
When an application directory deploys both a CRD and custom resources of that kind (e.g. `apps/envoy-gateway` and `apps/cert-manager`), Argo CD runs client dry-run validation during initial sync before any wave begins. Because CRDs are not yet registered on the API server during dry-run, `SkipDryRunOnMissingResource=true` is retained to bypass dry-run validation failures on uninstalled CRDs. Intra-component sync waves then apply CRDs at wave 0 and downstream custom resources at subsequent waves.
