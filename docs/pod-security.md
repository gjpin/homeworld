# Pod Security & User Namespaces

Workloads in this cluster are secured according to the [Kubernetes Pod Security Standards (PSS)](https://kubernetes.io/docs/concepts/security/pod-security-standards/), sandboxed with [gVisor](https://gvisor.dev/) wherever compatible, confined by SELinux on the standard runtime, and opted into [Kubernetes 1.37 User Namespaces](https://kubernetes.io/docs/concepts/workloads/pods/user-namespaces/) (`hostUsers: false`) on the standard runtime wherever supported.

Namespace-level Pod Security Admission (PSA) labels are managed declaratively in `apps/app-of-apps.yaml` through `syncPolicy.managedNamespaceMetadata`. Changes stage with Restricted `audit` and `warn` labels, with Restricted enforcement enabled once rendered and live admission results are verified clean. Namespaces without labels fall back to the k3s admission configuration (`host/files/k3s/psa.yaml`): enforce baseline, audit and warn restricted, with `kube-system` exempt.

Workloads requiring host integration, raw block devices, hostPath mounts, or root execution are isolated in dedicated namespaces with resource-scoped exceptions documented via `security.homeworld/exception-reason` annotations.

## User Namespaces

Kubernetes 1.37 User Namespaces (`spec.hostUsers: false`) map container UIDs/GIDs to unprivileged ranges on the host node, so even a container process running as UID `0` has no root privileges on the node.

gVisor cannot join a pod user namespace: its gofer fails to enter the pod's user namespace ([google/gvisor#13303](https://github.com/google/gvisor/issues/13303)). gVisor pods therefore keep the host user namespace; the sandbox kernel is their isolation boundary, and their non-root UIDs are unprivileged on the host anyway. User namespaces apply to the standard-runtime (runc) pods that support them.

## SELinux

Every node runs SELinux enforcing with the `k3s-selinux` policy and k3s's `selinux: true` ([fedora.md](fedora.md)):

- **runc pods** are confined as `container_t`, each pod with its own MCS categories.
- **gVisor pods** carry no SELinux label: runsc rejects an OCI spec with `process.selinuxLabel`, so a containerd shim wrapper (`host/files/libexec/runsc-selinux-strip`) removes it before runsc starts. gVisor's own kernel is their boundary.
- **`spc_t` exceptions** (runc pods whose host integration `container_t` denies, documented per resource): `otel-collector-node-agent`, `velero-node-agent`, and `homeassistant-zigbee2mqtt`. The Intel GPU device plugin runs as the policy's dedicated `container_device_plugin_t` type, and Jellyfin as plain `container_t`, reaching the allocated render node through the `container_use_dri_devices` boolean (`host/apply.sh` keeps it on). PSS `baseline` forbids custom SELinux types, so their namespaces enforce `privileged`. Privileged containers (Cilium, Longhorn's node components, csi-driver-nfs, kured, the k3s upgrade Jobs) run unconfined as `spc_t` by definition.

Volumes are labelled per pod: the Longhorn and NFS CSI drivers both drop `context=` mount options, so no StorageClass or PersistentVolume sets one. Longhorn filesystem volumes are relabelled with the pod's MCS categories when it mounts them. NFS files keep their `nfs_t` label, which `container_t` reaches through the `virt_use_nfs` boolean (`host/apply.sh` keeps it on).

## gVisor Runtime Sandboxing

To provide kernel-level defense-in-depth against container breakout vulnerabilities, the cluster utilizes [gVisor](https://gvisor.dev/) (`runsc`) via the `RuntimeClass/gvisor` definition. Its `runsc` handler is registered in containerd on every node by `host/apply.sh`, and the RuntimeClass itself is a k3s auto-deploying manifest (`host/files/manifests/homeworld-runtimeclasses.yaml`) that bootstrap installs and k3s re-applies on every start ([k3s.md](k3s.md)). Compatible workloads across every application namespace declare `spec.runtimeClassName: gvisor`. Operator-generated operands whose pod templates the CRD cannot set — CloudNativePG instance pods, Dragonfly instances, DocumentDB clusters, MariaDB Operator operands (instances, exporters, and SqlJobs), and RustFS Tenant pods — run on the standard runtime as documented exceptions: their `hostUsers` field is injected through the operators' supported mechanisms (`cnpg.io/podPatch`, MutatingAdmissionPolicy) where one exists, but the CRDs expose no runtime class field. Workloads spawned per-pipeline by the Woodpecker Kubernetes backend opt into gVisor per-step through backend options (`WOODPECKER_BACKEND_K8S_RUNTIME_CLASS_ALLOW_FROM_STEP` gates it at the agent). Cilium's socket load balancer is limited to the host namespace (`socketLB.hostNamespaceOnly`), because gVisor's netstack bypasses the per-socket BPF hooks: gVisor pods reach ClusterIP Services through the per-packet datapath instead.

Only workloads requiring direct host device access, host namespaces, raw block devices, kernel filesystem hooks, or a netlink feature gVisor lacks retain the standard container runtime.
